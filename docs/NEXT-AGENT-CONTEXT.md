## Цель продукта и согласованный сценарий

Бобби ведёт стажёра **с нуля до PR/MR по первой задаче Jira**. Это длительный ветвящийся сценарий, а не один ответ RAG и не заранее выданный большой чеклист.

1. Получить с бэкенда проверенный профиль: пользователь, команда, наставник, роль и имеющиеся данные. Не придумывать отсутствующие сведения и не спрашивать повторно известное.
2. Узнать, чем пользуется именно эта команда. Проверить ближайшую предпосылку, включая доступ к самой Jira — нельзя считать, что он изначально есть.
3. Если права нет, показать форму, получить подтверждение стажёра и подать заявку через централизованный сервис доступов.
4. Сохранить ID заявки и статус. Во время ожидания предлагать независимые полезные шаги.
5. После одобрения повторно проверить фактическое право. Отказ, задержка, частичное одобрение и смена команды меняют маршрут.
6. После получения задачи Jira определить следующие необходимые ресурсы: GitLab, инструкции, окружения и т. д. Каталог команды сам по себе не означает, что всё перечисленное нужно каждой задаче.
7. Считать цель достигнутой только после подтверждения существования PR/MR в GitLab и связи с выбранной задачей Jira. Сама модель не объявляет успех по предположению.

Модель должна гибко выбирать ближайший шаг и инструмент на основании фактов. Бэкенд проверяет параметры, права и допустимость перехода. Неизвестный результат проверки не равен отсутствию доступа.

## Что пользователь понимает под «без моков»

В Авито централизованный сервис доступов уже есть, но его внутренних API нам не предоставили. Поэтому **мы пишем его работающую имитацию**: Go HTTP API, PostgreSQL, JWT, несколько синтетических пользователей, команды, ресурсы, права, заявки, согласующие и история.

Агент вызывает реальные эндпоинты написанного сервиса. Нет runtime-ветки с зашитым JSON и фиктивного одобрения по таймеру. Другой пользователь-согласующий действительно одобряет/отклоняет заявку, и БД действительно изменяется. Фикстуры и тестовые двойники разрешены внутри автоматических тестов.

Права в нашей имитации не выдавай за изменение реальных корпоративных прав Авито. Имеющаяся учебная Jira — отдельная внешняя интеграция; её общий API-токен не является токеном конкретного стажёра.

## Контракт второго сервиса

Полный контракт — SDD-007. Основные точки:

- `POST /v1/auth/login` → `access_token`, `token_type`, `expires_in`; RS256 JWT, `aud` содержит `ai-buddy` и `team-access`; JWKS по `/.well-known/jwks.json`.
- `GET /v1/me` → `id`, `display_name`, `roles`, `teams`, `current_team_id`.
- `GET /v1/teams/{team_id}/resources` → **объект `{resources:[...]}`**, а не голый массив.
- `POST /v1/access/check` с `resource_id`, `capability` → `granted|missing|pending|unknown`.
- `POST /v1/access-requests` после подтверждения, с `Idempotency-Key`; чтение заявки и списка.
- `/v1/approvals` и решение назначенного согласующего; права читаются из актуальной БД, не из произвольной клиентской роли.
- PostgreSQL outbox → Kafka topic `team-access-events`; версия события 1, уникальный `event_id`, ID пользователя/ресурса/заявки, revision. Секреты не передаются в Kafka.

## Что уже реализовано основным агентом

### Существовавшая основа

Go API, RAG по Playbook и чеклисту, Qdrant, локальные embeddings, Qwen через OpenAI-compatible endpoint, HTTP/WebSocket заданий, Jira MCP чтения задач. Три старые кнопки сценариев и старая форма тестовой Jira-заявки. Старые маршруты не равны новому сервису доступов.

### Распределённая основа в текущей ветке

- `internal/distributed/jobs.go`: PostgreSQL jobs + outbox, Kafka publisher/consumer, lease, повторные попытки, условная запись результата, Redis-снимок статуса.
- `cmd/server/distributed_runtime.go`, `distributed_http.go`, `distributed_access.go`.
- `compose.distributed.yml`, nginx gateway, отдельные API и worker, PostgreSQL/Redis/Kafka/Qdrant/embeddings.
- Миграция `001_distributed_jobs.sql`.

Эта основа проверена интеграционными тестами с настоящей PostgreSQL и broker fixture; живой многоконтейнерный прогон с Kafka ещё не подтверждён.

### Новый сценарий — только первый участок

- `internal/scenario/scenario.go`: типы JSON версии 1 и детерминированный переход к ближайшему Jira-доступу.
- `internal/scenario/client.go`: реальный HTTP-клиент SDD-007; профиль, каталог, проверка, заявка, вход. При ошибке нет возврата фиктивных прав.
- `internal/scenario/store.go`: PostgreSQL-снимок с владельцем и оптимистической ревизией.
- `cmd/server/scenarios_http.go`: POST создания, GET снимка, POST advance и подтверждённой заявки; профиль пользователя проверяется через `/v1/me` сервиса, JWT не сохраняется в БД/промпте.
- `cmd/server/onboarding_web.go`: страница `/onboarding`, вход, виджеты формы и ожидания. Токен только в памяти страницы; localStorage содержит ID сценария, который снова проверяется по владельцу после входа.
- Миграция `002_scenarios.sql`.
- Маршруты включаются в distributed mode при заданном `TEAM_ACCESS_URL`.

- Сама LLM ещё не выбирает новые инструменты сервиса: первый участок запускает детерминированная логика. Это нужно честно отличать от готового адаптивного агента.
- Нет выбора задачи Jira внутри экземпляра сценария, последующих шагов GitLab/окружения и проверки PR.
- Нет автоматического применения Kafka-событий сервиса доступов к сценарию; пока нужен явный `advance`.
- Нет полноценного UI согласующего (это зона сервиса второго агента).
- Источники Confluence/GitLab и делегированные права конкретного пользователя ещё не подключены к новому сценарию.
- Полный Docker/серверный прогон и сборка текущего образа ещё не подтверждены.
- В старом коде есть demo cookie/API key и legacy mock/live Jira-пути. Не выдавай их за новую JWT-авторизацию; на сервере другой агент уже менял эти части, потребуется осторожная интеграция.
