# SDD-002: Очередь запросов и WebSocket-события AI-buddy

**Статус:** реализовано
**Ветка:** `codex/rag-integration`
**Владелец:** Hack&Change

## Проблема и цель

Синхронный `POST /v1/ask` держит HTTP-запрос открытым, пока идут поиск и генерация LLM. Несколько стажёров должны получать быстрый отклик интерфейса и выполнять независимые запросы параллельно, не перегружая локальную модель.

Цель: принимать вопрос как задание, выполнять задания ограниченным числом воркеров и сообщать клиенту о смене статуса через WebSocket. Существующий синхронный API остаётся доступным для совместимости.

## Пользовательский сценарий

1. Стажёр отправляет вопрос. Интерфейс сразу показывает «В очереди» и идентификатор задания.
2. Когда освободился воркер, статус меняется на «Готовим ответ».
3. По завершении интерфейс показывает ответ и источники. При ошибке показывает понятный сбой, не зависая.
4. Если соединение прервалось, интерфейс переподключается по ID задания или получает снимок состояния через HTTP.

## Контракты

| Метод | Путь | Результат |
| --- | --- | --- |
| `POST` | `/v1/jobs` | `202 Accepted`, `{id, status:"queued", query}` и `Location: /v1/jobs/{id}` |
| `GET` | `/v1/jobs/{id}` | Текущий снимок `{id, query, status, answer?, sources?, error?}` |
| `GET` WebSocket | `/v1/jobs/{id}/ws` | Сразу отправляет снимок, затем JSON-события с теми же полями |

Статусы: `queued → running → completed` либо `queued/running → failed`. Завершённое задание неизменно. Неизвестный ID возвращает `404`. Пустой или слишком короткий вопрос — `400`. Полная очередь — `429` с явной ошибкой. Каждое задание получает уникальный непредсказуемый ID.

## Планировщик

- Очередь FIFO с ограниченной ёмкостью; `JOB_WORKERS` (по умолчанию 2) независимых воркера, `JOB_QUEUE_SIZE` (по умолчанию 32).
- Воркеры выполняют существующий RAG-поиск и вызов LM Studio; число одновременных вызовов LLM ограничено числом воркеров.
- HTTP-обработчик не ждёт LLM. Контекст задания живёт после завершения исходного HTTP-запроса; на задание действует отдельный таймаут `JOB_TIMEOUT_SECONDS` (по умолчанию 180).
- Состояние и подписчики защищены от гонок. Медленный WebSocket-клиент не блокирует воркер; если он отстал, он может получить актуальный снимок через `GET`.
- Завершённые задания хранятся в памяти ограниченное время; при перезапуске сервера исчезают. Для продакшена потребуется внешнее хранилище/очередь.

## WebSocket и безопасность

- Использовать `github.com/gorilla/websocket` с проверкой Origin по умолчанию, без `CheckOrigin: true`.
- При пустом `API_KEY` соединение доступно на локальном интерфейсе, как существующий API. При заданном ключе первое сообщение клиента — `{"api_key":"..."}`; сервер не передаёт данные до проверки и закрывает соединение при ошибке/таймауте. Ключ не помещается в URL.
- Один писатель на WebSocket-соединение, ограниченное время записи, корректное закрытие подписки.
- Не отправлять текст вопроса или ответ в логи. Индекс Qdrant и LM Studio не публиковать наружу.

## Проверка и критерии приёмки

1. Два блокирующих тестовых задания при двух воркерах одновременно переходят в `running`; третье ждёт в `queued`.
2. Заполнение очереди возвращает `429`, не теряя принятые задания.
3. WebSocket получает снимок при подключении и события до `completed`/`failed`.
4. Отключение WebSocket не отменяет задание; `GET` возвращает итог.
5. При ошибке LLM задание становится `failed`; интерфейс показывает ошибку.
6. Проверены `400`, `404`, защита API-ключом и Origin.
7. `go test -race ./...` проходит в Linux-контейнере с CGO; воспроизводимое покрытие прикладного кода превышает 80% согласно требованиям кейса.

## Результат проверки 9 ноября 2026

- `go test -coverpkg=./... -coverprofile=coverage.out ./...`: суммарное покрытие **90,3%**; Dockerfile сохраняет порог 90%.
- `CGO_ENABLED=1 go test -race ./...` в `golang:1.23-alpine` с `gcc` и `musl-dev`: все пакеты прошли.
- Живой сервер: два `POST /v1/jobs` вернули `202` за 31 мс суммарно; оба задания наблюдались в `running`, затем в `completed` по WebSocket.
- Проверено в браузере: две карточки вопросов одновременно показывали «Готовим ответ», затем обе показали ответы и карточки источников.

## Границы

В этой версии нет распределённой очереди, гарантии сохранения заданий после перезапуска, отмены задания и потоковой выдачи токенов LLM. WebSocket передаёт смены состояний и готовый ответ.
