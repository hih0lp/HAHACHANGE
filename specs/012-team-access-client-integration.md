# SDD-012: связь двух Go-сервисов и чата Бобби

## Состав

`cmd/server` — API Бобби, асинхронные задания, чат и сценарий первой задачи. `cmd/team-access` — отдельный API профиля, каталога команды, прав и заявок по контракту SDD-013. Они соединяются через `TEAM_ACCESS_URL=http://team-access:8080` во внутренней сети Compose. PostgreSQL хранит оба набора данных; сервис доступа публикует события через outbox в Kafka topic `team-access-events`.

## Идентичность в чате

Главный чат получает демо-cookie при открытии `/` и вызывает `POST /v1/team-access/session`. API Бобби входит в сервис доступа под настроенным тестовым пользователем (`TEAM_ACCESS_CHAT_USERNAME`, по умолчанию `intern`) с паролем из окружения; JWT хранится в `sessionStorage` вкладки и передаётся в `Authorization` при создании задания. API проверяет JWT через профиль, но не загружает состав команды и права в промпт. Токен задания хранится в Redis с ограниченным сроком жизни и передаётся worker через контекст; он не записывается в PostgreSQL/Kafka и не передаётся модели.

Worker получает актуальный каталог инструментов через MCP `tools/list` от Jira (`/mcp`, если включён live-режим) и team-access (`/team-mcp`, если есть JWT). Модель сама выбирает инструмент по смыслу запроса. Нативный вызов функции либо структурированный JSON-вызов модели исполняется worker через MCP `tools/call`; результат возвращается модели для ответа. Список пользователей, команд и прав не зашит в промпт или роутер. MCP-адаптер team-access в API Бобби проксирует вызовы в HTTP API отдельного сервиса с JWT пользователя; границы доступа проверяет сервис. Доступны чтение профиля, участников команды, ресурсов и проверка права. Отправка заявок через MCP пока не предоставлена.

Без JWT worker не получает инструменты team-access и не утверждает персональные права. Некорректный JWT не подменяется демо-пользователем. Состояние `missing` означает отсутствие grant только в прототипе; реальный Jira-доступ этим не определяется. Каждый вопрос вызывает актуальные инструменты по необходимости. Результаты не дают Бобби полномочий одобрять заявку: решение принимает отдельный пользователь-согласующий через сервис.

## Сценарий первой задачи

`POST /v1/scenarios/login` проксирует вход. `/v1/scenarios/*` использует проверенный JWT для профиля, ресурсов, проверки права и заявки. Состояние сценария хранится в `ai_scenarios` и не считает отправку заявки одобрением.

API Бобби читает `team-access-events` отдельной Kafka-группой. Уникальный `event_id` хранится в `ai_scenario_events`; повторная доставка не меняет состояние второй раз. Решение по связанной заявке помечает ожидающий сценарий `needs_refresh`. Следующий `GET /v1/scenarios/{id}` проверяет право через сервис с JWT пользователя, сохраняет новый шаг, а страница опрашивает сценарий раз в пять секунд. Само Kafka-событие не считается доказательством grant.

## Ограничения развёртывания

Бобби доступен в прототипе по адресу Tailscale `100.105.236.12:18000` и localhost `127.0.0.1:18000`; HTTP API team-access опубликован только на localhost `127.0.0.1:18080`. Демо-cookie Бобби связывает историю чата с браузером, а не с JWT-пользователем; для многопользовательской системы понадобится заменить его на проверенную авторизацию и изолировать историю по `sub`. Пароль тестового пользователя остаётся только на сервере.

## Проверка

`go test ./...`; `scripts/team-access-smoke.ps1` проходит профиль двух пользователей, каталог, pending, повторный запрос, изоляцию, approve, reject и grant. Сквозной запрос «Кто у меня в команде?» должен вернуть состав только разрешённой команды; запрос «Покажи таски из Джиры» должен получить реальные задачи через Jira MCP без раскрытия имён внутренних инструментов. Проверять, что JWT не попал в PostgreSQL, Kafka, ответ модели и публичный ответ.
