# SDD-015: каталог команды и сервис прав с универсальными формами

## Владение данными и версии

`team-access` в режиме `team` владеет пользователями, командами, членством, входом и JWT. `access-rights` в режиме `rights` владеет ресурсами, grant, заявками, решениями, outbox и формами. Это отдельные контейнеры и базы `aibuddy_teams` и `aibuddy_rights` в одном экземпляре PostgreSQL; сервисы не читают таблицы друг друга. Существующий RSA-ключ сохраняется в томе, доступном сервису прав только на чтение. Контракты остаются под `/v1/`; опубликованные формы имеют неизменяемые версии `id + version`.

Сервис прав проверяет подпись, срок и аудиторию JWT и при каждом обращении к командному ресурсу запрашивает членство у каталога команд с токеном пользователя. Недоступность каталога означает `503`, отсутствие членства — `404`; сервис не выдаёт данные на основании названия команды, переданного моделью. Согласование требует текущую роль `approver` в соответствующей команде. JWT не передаётся модели.

## HTTP API

Каталог команд сохраняет `POST /v1/auth/login`, `GET /v1/me`, `GET /v1/teams/{id}/members`, `GET /.well-known/jwks.json`. Сервис прав сохраняет `GET /v1/teams/{id}/resources`, `POST /v1/access/check`, `/v1/access-requests` и `/v1/approvals` из SDD-013.

Сервис прав добавляет:

- `GET /v1/forms`: опубликованные актуальные версии форм;
- `GET /v1/forms/{id}`: заголовок, описание, тип, версия, JSON Schema и UI Schema;
- `POST /v1/forms/{id}/validate`: `{values}` → результат серверной проверки;
- `POST /v1/forms/{id}/submit`: `{version,values,confirmed:true}` и `Idempotency-Key` → ID и статус;
- `GET /v1/form-submissions/{id}`: статус своего общего обращения;
- `POST /v1/forms`: публикация новой неизменяемой версии для пользователя с ролью `approver`.

Тип `access` создаёт существующую заявку `pending`, записывает ID и версию формы и требует отдельного согласующего. Тип `general` сохраняет обращение `submitted` и не выдаёт право. Повтор с тем же ключом и теми же данными возвращает прежний результат; другие данные дают `409`. Внешние ссылки в схемах JSON Schema не допускаются в рабочем реестре. Административный API публикует схемы без перезапуска контейнера; UI отображает поля по схеме с общим вводом JSON для составных значений.

## Агент и подтверждение

MCP-каталог, который worker получает через `tools/list`, расширяется средствами поиска форм и чтения схемы. Бобби сам определяет уместность формы, получает `form_url` и предлагает пользователю открыть её. Словаря пользовательских фраз и выбора конкретной формы по ключевым словам в worker нет. Модель не имеет инструмента отправки: пользователь проверяет поля и нажимает кнопку в веб-форме, после чего приложение передаёт JWT, подтверждение и ключ идемпотентности сервису прав. Бобби сообщает об отправке или выдаче права только по ответу сервиса.

Сервисы предоставляют HTTP/MCP-контракты независимо от модели. Адаптер worker преобразует каталог MCP в формат подключённой модели; локальный и удалённый OpenAI-совместимые API используют одинаковую семантику инструментов. Секреты модели и сервисов не входят в промпт.

## Миграция и приёмка

Перед переключением сохранить резервную копию исходной базы. После создания схем перенести старые записи `ta_users`, `ta_teams`, `ta_memberships` в базу команд, а `ta_resources`, `ta_grants`, `ta_requests`, `ta_audit`, `ta_outbox` — в базу прав. Сравнить количества и IDs; исходные таблицы при первом запуске не удалять. Проверить вход, состав своей команды и отказ на чужую, каталог ресурсов, pending → approve → grant, повтор запроса, общую форму и публикацию новой версии без изменения кода UI. Проверить запросы Бобби к Jira и сервисам, а также отсутствие имён внутренних методов в пользовательских ответах.
