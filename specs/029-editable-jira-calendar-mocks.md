# SDD-029: Editable Jira and Calendar MCP simulators

Two independent Go services provide the existing Jira and Google Calendar MCP tool names to an isolated Bobby stack. The Jira simulator loads `fixtures/mock/jira.json` on each request; the calendar simulator loads `fixtures/mock/calendar.json` on each request. No response is cached, and invalid JSON returns an error. The source snapshots were read on 13 November 2026 from the live demo MCP services. They contain seven SCRUM issues and the mentor calendar's seven upcoming events. Credentials and attendee email addresses are excluded. Mock URLs in issue data identify the captured demo Jira, but the simulator never calls Jira or Google.

The Jira fixture holds `project_key` and ordered `issues`; each issue has key, summary, status, status_category, description, optional due/start dates, optional assignee account ID/name, URL, and optional display-name-to-value fields. MCP provides issue detail, recent list, assigned list and all nonempty fields. The read-only `/rest/api/3/search/jql` endpoint supports the existing reminder scan, including status category. Bobby's `JIRA_MODE=mock` accepts an internal HTTP origin without live credentials; `live` retains its HTTPS and credential validation.

The calendar fixture holds `calendar_id`, `summary`, `time_zone`, and `events` with IDs, start/end RFC3339 timestamps, titles, optional descriptions and links. Event queries return Google-like `data.items`; free/busy derives UTC busy intervals from the same events, avoiding inconsistent slots. Queries use half-open range overlap and retain the 31-day limit. The calendar MCP verifies the bearer against team-directory `/v1/me` and the configured demo subject. Both binaries bind only to `127.0.0.1:8080` when launched locally; Compose explicitly sets `MOCK_LISTEN=:8080` on its private network, without publishing the mock service ports to the host.

For an isolated test launch, use a different Compose project name and `compose.distributed.yml` plus `compose.mock.yml`, with `BOBBY_LOCAL_PORT=18001`, `BOBBY_REMOTE_BIND=127.0.0.2`, `BOBBY_REMOTE_PORT=18001`, `BOBBY_TEAM_PORT=18082`, and `BOBBY_RIGHTS_PORT=18083`. The test stack uses its own PostgreSQL/Redis/Kafka and mounts the two JSON files read-only; the production Compose project and URL remain unchanged. The fixture files are edited on the host and are reloaded at the next MCP or reminder request. Validate MCP tools/list and tools/call, mock Jira search, team bearer denial, empty and changed ranges, then ask Bobby about SCRUM-7, personal tasks, events and mentor busy time.

The test worktree requires its own untracked `.env`, based on `.env.example`: set independent `POSTGRES_PASSWORD`, `SESSION_SECRET`, and the three `TEAM_ACCESS_*_PASSWORD` values (each password at least 12 characters), a reachable `LLM_URL` and `LLM_MODEL`, and `TEAM_JIRA_ACCOUNTS_JSON` mapping `intern` to the `assignee_account_id` in `jira.json`. Do not use production Jira or Google credentials. `compose.mock.yml` overrides the Jira and calendar endpoints and enables `JIRA_MODE=mock`; `TEAM_JIRA_ACCOUNTS_JSON` is needed so the personal-task query resolves the same assignee as the fixture. On the Windows host, start from this worktree with:

```powershell
$env:BOBBY_LOCAL_PORT='18001'
$env:BOBBY_REMOTE_BIND='127.0.0.2'
$env:BOBBY_REMOTE_PORT='18001'
$env:BOBBY_TEAM_PORT='18082'
$env:BOBBY_RIGHTS_PORT='18083'
docker compose -p bobby-mocks -f compose.distributed.yml -f compose.mock.yml up -d --build
```

Open `http://127.0.0.1:18001/` on the server, or forward that port through SSH. The same Compose command without `compose.mock.yml` is not the test setup. Stop only the test project with the matching `-p bobby-mocks` and both Compose files. Do not use `down -v` unless intentionally resetting test chats, accounts and keys. Changing either fixture file on the host needs no restart.

For `jira.json`, `project_key` is a nonempty string and `issues` is an array of objects with unique project-prefixed `key`, nonempty `summary` and `status`, plus `status_category`, `description`, `assignee_account_id`, `assignee_name`, and `url`. `due_date` and `start_date` are `YYYY-MM-DD` strings or `null`; `fields` may supply additional display-name keys. For `calendar.json`, `calendar_id`, `summary`, and `time_zone` are strings and `events` is an array of objects with unique `id`, nonempty `summary`, `description`, `status`, and `start`/`end` objects containing RFC3339 `dateTime` and a `timeZone`. End must follow start. On every read, Jira checks the project, issue key, summary, status, date format and key uniqueness; calendar checks ID, timezone presence, event ID, summary, interval and ID uniqueness. Malformed JSON and failed checks produce an MCP tool error instead of reusing earlier data.

Verification on 13 November 2026: `go test ./...` passed during the initial build. Local Jira MCP `tools/list` exposed four tools, and `jira_get_issue(SCRUM-7)` returned the captured dates, assignee and empty description. Server images built successfully. The calendar MCP returned two events and two corresponding busy intervals for 17–20 November. A separate test-only `.env` was provided with the user's approval; the production `.env` was neither read nor copied. The `bobby-mocks` Compose project runs on the server with its own database, queue, cache, keys and image tags. The mock MCP containers have no published host ports. The production containers continue to run with their original configuration.

The test chat at server localhost port 18001 issued an intern team session and completed questions about SCRUM-7, the intern's assigned tasks, and the 17–20 November events. It reported SCRUM-7 as in progress, assigned to Gapshin Mihail, starting 10 November, due 13 November, with an empty description. The assigned-task answer returned SCRUM-7. The event answer returned 17 November 15:30–16:00 MSK and 19 November 16:00–17:00 MSK. The captured SCRUM-7 summary itself is a nonsense string beginning with a backslash; it is preserved literally in `jira.json`, not reconstructed from PowerShell's garbled terminal output. The team directory accepts the internal HTTP Jira origin only when `JIRA_MODE=mock`; the production HTTPS validation remains in force.

The initial test-chat answer about 19 November availability also claimed 13:00–14:00 MSK, an interval absent from the fixture and MCP result. Bobby now formats direct calendar questions from MCP data in the mock stack: events from `items` and occupied time from `busy`. This keeps the answer tied to the editable JSON and prevents the model from adding a slot. The formatter tests check that UTC 13:00–14:00 becomes 16:00–17:00 MSK and reject missing data. The production answer path remains unchanged.

Final end-to-end check: the event question returned precisely the two fixture events and their 15:30–16:00 and 16:00–17:00 MSK times. A repeat of the busy-time question completed with exactly `19.11.2026 16:00–17:00 МСК`; the earlier fabricated interval was absent. One intervening attempt remained `running` after 150 seconds and the worker log reported a model tool-call-limit error. The planner instruction now explicitly maps availability questions to `needs_availability`, reducing that route's dependence on the answering model's tool selection. Model latency and occasional planner/tool-call failures remain possible; the mock services themselves return deterministically for a given JSON snapshot.

Refresh on 13 November 2026: queried the live Jira MCP `jira_list_issues`, `jira_get_issue`, and `jira_get_issue_fields` for all seven SCRUM issues. The existing `jira.json` already matched the live issue cards for keys, summaries, statuses, descriptions, dates, assignee IDs/names and URLs, so no task values changed. Queried the live Google Calendar MCP for events and free/busy from 13 November to 10 December 2026: seven events and seven busy intervals. `calendar.json` now stores the real event IDs, all returned descriptions and `htmlLink` URLs, alongside the unchanged times. Attendees, organizers, email addresses, opaque calendar account ID and OAuth data are omitted; `calendar_id` stays a local alias. Bobby's mock chat converts HTML event descriptions to readable text and presents event links, while the MCP still returns the original descriptions.

The refreshed test chat exposed a routing issue: when the model planner requested both events and free/busy for an event question, Bobby returned only busy intervals. In the mock stack it now includes both verified result sets in one answer. Each result is formatted from the corresponding MCP payload; a failed tool is reported explicitly rather than filled in by the model.

Refresh verification: the fixture comparison matched all seven Jira cards and seven calendar events field by field; the seven live `busy` intervals matched the event start/end pairs. The test Docker build passed `go test ./...`. In the isolated chat at `127.0.0.1:18001`, SCRUM-7 returned start 10 November, due 13 November, in-progress status and empty description. The event question for 17–20 November returned both event names, times, cleaned descriptions and live event links. The availability question for 19 November returned only 16:00–17:00 MSK. The production MCP endpoints and containers were not changed.

A later test pass exposed model variance: although `jira_get_issue(SCRUM-7)` returned a valid card through the mock MCP, the model twice claimed the task was absent. In the mock stack, for questions containing an explicit Jira key and needing no other evidence, Bobby now fetches each unique key's card through the configured MCP and formats the verified facts directly. This is generic key extraction and MCP lookup, with no issue facts encoded in Go. Missing description and dates are stated explicitly; a failed lookup is marked as unverified. Requests that also need forms, team details, personal-task lists, calendar evidence or recommendations keep their respective routes.
