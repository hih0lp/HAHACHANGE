# SDD-027: Qwen 3 1.7B query filter experiment

The experiment runs in a separate branch and deployment. The first model call uses `ROUTER_MODEL=qwen3-1.7b` to produce `cleaned_question` and zero or more categories: `jira`, `calendar`, `gitlab`, `documents`, `rights`, `team`. The original question remains available to Bobby and history. The filter is instructed to preserve negation, dates, task keys, names, and every part of a mixed request. The server rejects malformed JSON, blank cleaned text, unknown or duplicate categories. A failed filter cannot silently become a factual answer.

The existing main-model planner remains responsible for calendar intervals, request form selection, personal Jira intent, and recommendation intent. The smaller model was inaccurate when asked to produce those fields along with categories. Live testing also showed false-positive source categories, so the planner independently validates the necessary source categories. When it supplies a validated `required_categories` array, that array replaces the first model's category suggestion; specialised planner flags can still add sources required for a verified action. The filter output remains logged for comparison. The worker offers Bobby only MCP tools from the selected service endpoints. `documents` uses the existing RAG index and search on the cleaned question; it does not create another document index. The team category prefetches the authenticated profile and members so Bobby can retain verified context. MCP tokens never enter the model prompt or trace.

Jira detail and list results retain their `status` string and add `status_category` when Jira supplies it. A missing category is omitted. The agent must not infer completion or due date from status. A simple personal task list is rendered from structured assigned-issue fields after the planner confirms that no other subject was asked; the short list never fabricates a description. The route trace records category selection, MCP tool names, success flags, and latency keyed by job ID without user text or credentials.

Recommendation evidence fetches open MR data for available GitLab projects selected from the live project catalogue, without a fixed project ID. The GitLab MCP exposes `gitlab_identity` from the user's bound token; only MR records whose author or reviewer ID matches that identity are labeled personal. A project listing does not prove personal work. The `gitlab_projects` argument schema allows an omitted project. Placeholder `.invalid` URLs are removed from tool evidence before the answer model sees them. If identity, projects, or MR checks fail, the recommendation cannot claim verified GitLab evidence.

Evaluation compares the baseline with the branch on single-service, mixed-service, continuation, empty-result, unauthorized, and unavailable-MCP cases. The small model's category errors are reported separately from the final answer: the second planner can recover a needed category, but the experiment only passes if the user receives grounded facts and no unrelated service is queried. Personalized recommendations require evidence from the team, Jira, GitLab, and documents; a project listing alone does not prove individual skill.

The first live probe found that the 1.7B filter sometimes adds calendar to a specific Jira question and GitLab to a documentation question, and misses rights or calendar in mixed requests. The existing 8B planner also sometimes marks a specific issue question as a personal-list request. Jira SCRUM-7 detail was grounded (status `В работе`, due `2026-11-13`, start `2026-11-10`); the old generated personal-list answer mislabeled summary as description, motivating structured rendering. An empty 14 November calendar result was returned but the answer cited an unrelated profile URL. These are open quality failures; the experiment must not be promoted to the production chat until the remaining live cases and category precision pass.

In a later GitLab probe, `gitlab_identity`, `gitlab_projects`, and `gitlab_merge_requests` all succeeded, but the answer model called the MR list again and exceeded the three-minute test deadline. A planner flag now lets a request solely for open MR listings use a compact server-rendered response from verified MCP records. This flag is semantic; it is not selected with a keyword list. A mixed or analytical request still reaches Bobby with selected tools. The latency and relevance gate remains open until the live retry passes.

The GitLab list retry passed in 26 seconds with seven linked open MR records, correctly described as belonging to projects visible to the account rather than all authored by the user. A document question timed out when the 1.7B filter added an unrelated GitLab category. The independent planner category check was added to remove that false positive. The initial recommendation probe could not search RAG because the one-shot container was attached only to the distributed service network; the test launcher now attaches the existing RAG network as well. A fresh recommendation check is still required.

With both networks attached, the documentation request passed with cited playbook fragments in 95 seconds. The recommendation fetched all four sources but answer generation exceeded three minutes. Recommendation evidence was then reduced to three relevant document chunks, one team profile and member list, assigned Jira issues, GitLab identity and compact personal MR metadata. Since these MCP calls already completed, Bobby synthesizes this particular answer without another tool catalogue. Missing GitLab identity or MR results fail closed rather than producing a claimed personal recommendation.

The compact free-text recommendation completed in 163 seconds but incorrectly treated project-wide Jira records as the user's work and interpreted no matching open MR as lack of GitLab experience. The final recommendation route therefore passes only assigned Jira issues, verified personal open MR metadata, the team profile and members, and cited document chunks. Bobby must return up to three JSON steps with source IDs. The server validates that each step cites both a personal issue/MR and a document chunk, rejects unknown IDs and foreign Jira keys, and renders only verified source links. An empty result honestly reports insufficient evidence. No matching open MR is described only as a result within the checked open MR set, not as a skill assessment. A live retry of this stricter path remains required.

The first strict-output retry failed because this LM Studio endpoint rejects `json_object`; it accepts `json_schema` or `text`. The endpoint's documented JSON Schema response format is now used for the recommendation. Qwen3's documented `/no_think` switch is applied to this short synthesis, and empty responses log the finish reason and reasoning length without logging personal content. A live retry is still required before calling this scenario successful.

The first JSON Schema retry returned an empty answer; the subsequent `/no_think` retry produced JSON but its step lacked both personal and document evidence, so validation correctly rejected it. The schema now restricts source IDs to the verified set, and the renderer drops steps lacking the required evidence pair. If none remain, it returns an explicit insufficient-evidence answer. This is a safe failure, not a successful personalized recommendation; the final live retry is pending.
