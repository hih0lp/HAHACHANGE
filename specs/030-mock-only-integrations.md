# SDD-030: Bobby uses editable Jira and Calendar mocks

This specification supersedes the live Jira and Google Calendar runtime paths described in SDD-010, SDD-011, SDD-016, SDD-020, SDD-022 and the earlier deployment portions of SDD-029. The distributed stack runs `mock-jira` and `mock-calendar` from `compose.distributed.yml`, mounts `fixtures/mock/jira.json` and `fixtures/mock/calendar.json`, and points API, worker, team directory and calendar reminders to those services. Jira accepts `off` or `mock`; `live` fails configuration validation. The old Google OAuth calendar service, bootstrap tool and Compose overlay are removed. The disabled legacy Jira issue-creation adapter, its access-request file store and the duplicate Jira MCP route on the Bobby API are removed; access forms continue through the separate rights service. The active MCP overlay retains GitLab only. Team directory, access rights, forms, chat history, Jira and GitLab reminders, calendar reminders, search, queue, and other tools remain available.

The user controls Jira project identity and the calendar demo subject through `.env` (`JIRA_PROJECT_KEY`, `CALENDAR_DEMO_SUBJECT`). The test overlay sets separate image tags and runs the existing GitLab MCP binary against the test team directory. Only that GitLab MCP container also joins the demo GitLab network (`GITLAB_DEMO_NETWORK`); its API origin, subject and read-only token file come from `.env` (`GITLAB_API_ORIGIN`, `GITLAB_DEMO_SUBJECT`, `GITLAB_DEMO_TOKEN_PATH`). The token is not copied into Git. Set `GITLAB_MCP_URL=http://gitlab-integration:8080/mcp` for the test API and worker. Do not attach the test API or worker to the working stack's network: shared service names such as `postgres` resolve ambiguously. The mock JSON files remain the only source of task and event facts. Editing either mounted JSON takes effect on the next request without a container restart. See SDD-029 for the JSON structures, read-time validation and fixture refresh provenance.

The LLM planner chooses whether a question needs a specific Jira card, the user's assigned issues, calendar events, availability, forms, team directory, or other evidence. For a specific issue it returns `needs_jira_issue` and `jira_issue_keys` copied from the question. Bobby calls `jira_get_issue` for the selected keys and formats the MCP results. No issue-key regular expression, fixed key list, fixture title or phrase matching is used to route a user question. The Jira adapter still validates its tool arguments; this does not select tools or supply candidate values to the model. A missing card is reported as unverified. Questions about assigned issues continue to use the team profile account ID and `jira_list_assigned_issues`.

The team directory remains the source of membership and mentor roles. Bobby omits `jira_profile_url` from team evidence supplied to the answer model because demo seed data can contain placeholder or container-only profile links. Names, roles and account IDs remain intact; this is output sanitization, not question routing or a list of candidate values.

For calendar questions the planner selects events, availability, or both and supplies a bounded period. The mock chat formats event details and free/busy intervals from the corresponding MCP payloads; if both tools are selected, both results are shown. HTML descriptions become plain text and source links are kept. The mock services do not contact Jira Cloud or Google Calendar at runtime.

Acceptance: Docker Compose with `compose.distributed.yml` must resolve Jira and Calendar endpoints only to the mock services; `compose.active-mcp.yml` must retain GitLab without overriding Calendar. Full `go test -cover ./...` must pass in the Docker build and report per-package coverage. End-to-end questions must cover a model-selected Jira card, personal Jira tasks, calendar events, availability, forms, team and reminders. The production deployment must be updated by an operator with access to its private `.env`; the collaborating account must not read that file, per the user's earlier decision.

Verification on the isolated `bobby-mocks` project (13–14 November 2026): Docker `go test -cover ./...` passed after removing the duplicate Jira MCP route. Coverage was 42.6% for `cmd/server`, 26.4% each for `cmd/mock-jira` and `cmd/mock-calendar`, 56.4% for the GitLab MCP, 21.5% for team-access, 90.5% for RAG, 71.7% for scenario, 10.6% for teamaccess and 88.9% for knowledge. The two mock package tests verify fixture reload, personal filtering, date validation and calendar range selection; server tests cover planner selection, card formatting, forms and reminders. The main package coverage is limited by server startup and external service paths, so the live chat checks below are also required.

The chat answered the specific SCRUM-7 question with the mock card's status, assignee, start date, due date and empty description. It listed SCRUM-7 as the signed-in intern's assigned task. The 17–20 November calendar question returned exactly the two fixture events and their two busy intervals; the 19 November busy question returned 16:00–17:00 MSK. A team question returned the mentor and two other members from the team directory. Asking to obtain access returned `[Заявка на доступ](/forms/access-request)`; `GET /v1/forms/access-request` returned form version 1. The final API build returned HTTP 200 for the chat and HTTP 404 for the former API `/mcp`; `MCP_URL` and `CALENDAR_MCP_URL` point only to the mock services. The final `GET /v1/reminders`, `/v1/calendar/reminders` and `/v1/gitlab/reminders` checks all succeeded on the test project; their current reminder lists were empty. The production project was not redeployed because its private `.env` remained inaccessible by the user's instruction.
