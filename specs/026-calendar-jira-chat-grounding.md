# SDD-026: Calendar, Jira dates, and readable answers

The intern asks about onboarding events and mentor availability in one selected mentor calendar. The calendar MCP reads event details and free/busy intervals from `CALENDAR_MENTOR_ID`; the older onboarding calendar ID is no longer used for reads or notifications. Relative dates are interpreted in Europe/Moscow. The agent receives current Moscow date and time. Calendar questions for today, tomorrow, and named dates prefetch exact local-day events before the model responds; general calendar questions prefetch the next 30 days. Slot questions also prefetch free/busy. Calendar notifications use the same selected calendar.

Jira issue details include due date and start date (`duedate` and this demo Jira's `customfield_10015`). For later questions about other fields, `jira_get_issue_fields` fetches all nonempty fields with their Jira display names. The agent must not infer dates from status or project documents. A missing description remains missing; summary is labelled as the task title. The verified team profile is included in the agent context for personalized answers. Recommendations still need separate source verification and coverage work before they can be considered complete.

The chat renders headings, lists, emphasis, and safe HTTPS links as DOM nodes for both new and restored answers. It never inserts model HTML. Existing task notifications retain their distinct amber cards. Recommendation questions prefetch the current team profile and members, Jira issues, and available GitLab projects and MRs. If a required source is unavailable, the agent returns an explicit limitation instead of a fabricated personalized recommendation. The agent must not infer a person's skill from generic documentation. Full recommendations require the pending per-person GitLab MCP deployment.

Tool descriptions explain the evidence each tool actually returns. The Jira list is explicitly marked as a discovery view without dates or descriptions; facts about each issue require its detail tool. The calendar event tool identifies the selected mentor calendar and distinguishes scheduled events from free/busy intervals or documentary references. The agent instruction requires checking every relevant issue or source before a combined answer. These are general evidence rules, not a list of user phrases. Tool descriptions alone do not enforce tool invocation; model-driven tool selection and verification remain a separate reliability concern.

Calendar routing is model-driven for every question. A planning call returns whether event and/or availability evidence is needed and a Moscow RFC3339 interval. The server rejects malformed or greater-than-31-day intervals before MCP calls. This replaces the earlier keyword and Russian month parser, so wording variants are not enumerated in code. If planning or calendar access fails, the answer prompt says schedule facts are unverified.

Published meeting windows belong to the mentor calendar's events. The planner requests event evidence for those windows and requests free/busy only when the user asks to calculate free time or inspect busy intervals. This distinction is stated in the planning instruction to reduce the risk of treating a published window as an inferred available slot.

The planner classifies the requested period semantically. For the ongoing or following week, the server computes Monday boundaries in Europe/Moscow; for a current or future schedule it clips elapsed time unless the user explicitly requested history. The answer may only use events in the verified interval. This prevents past mentor windows from appearing as upcoming events.

After an empty verified calendar result, the answer states the checked interval and absence of events without suggesting that the user check the same calendar again or substituting documentary mentions of possible events.

The short Jira issue result always includes `description`, even when it is empty. An empty description is stated as empty; the title is never reinterpreted as description or an encoding failure.

Personal Jira questions are classified by the model in the same planning call as calendar and form intent. The worker reads the current employee's verified `jira_account_id` from the authenticated `team_profile` MCP result and calls `jira_list_assigned_issues` with that ID. The Jira adapter restricts JQL to the configured project, validates the account ID, and checks the assignee on every returned issue. A demo-only ID causes an explicit identity-mapping response rather than an invented personal list. The project-wide `jira_list_issues` output includes assignee metadata and is labeled as project-wide. Both searches return due dates and the configured project key, but omit description and start date entirely; detail calls remain authoritative for those fields. The personal search reports when its 50-result page is truncated.

Recommendation intent is also classified by the planner instead of matching Russian word fragments. The GitLab project is no longer fixed to one numeric ID in source code. The available project catalogue is evidence of access only; MR evidence must be fetched for a selected project before making claims about the employee's work. Full recommendation coverage remains pending.
