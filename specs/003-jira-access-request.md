# SDD-003: Заявка на доступ через Jira

**Статус:** реализовано в mock; live-адаптер готов, ожидает локально заданный API-токен

## Сценарий

Стажёр первой недели спрашивает AI-buddy, как получить доступ к пространству команды. Помощник отвечает по открытому чек-листу, показывает источник и предлагает создать **тестовую** задачу в Jira. Стажёр видит проект, название и описание задачи и явно подтверждает создание. Jira или её локальная имитация возвращает ключ и статус; AI-buddy показывает их и сохраняет для повторного открытия страницы.

Открытый чек-лист требует запросить доступ, но не описывает внутренний процесс Авито. Демонстрационная задача не выдаётся за регламент или интеграцию с корпоративной Jira Авито.

## Контракты и границы

- `POST /v1/access-requests`: создать запрос с `resource` и `reason` после подтверждения в UI. Ответ `201` содержит локальный ID, Jira-ключ, статус, режим (`mock`/`live`), ссылку (только для live) и следующий шаг.
- `GET /v1/access-requests/{id}`: повторно получить сохранённый результат.
- `GET /v1/access-requests`: показать последние запросы этого демонстрационного пользователя.
- Отдельный адаптер `IssueTracker.CreateIssue(ctx, ...)` для mock и Jira Cloud REST API v3. Выбор через `JIRA_MODE`; по умолчанию mock.
- В live-режиме используются `JIRA_BASE_URL`, `JIRA_PROJECT_KEY`, `JIRA_ISSUE_TYPE` и отдельные учётные данные API. Значения проверяются при запуске, секреты берутся только из окружения и не попадают в репозиторий или ответы API.
- Данные запроса синтетические. Текст задачи явно содержит пометку «Hack&Change: тестовая заявка». Никаких ФИО, реальных сотрудников или закрытых инструкций.
- Локальный результат сохраняется на диск атомарно в Docker volume. Ошибка Jira не считается успешным действием; UI показывает сбой и позволяет повторить попытку.
- Роли в прототипе имитируются; операция доступна только демонстрационному стажёру. В реальном внедрении роль должна проверяться существующей системой авторизации Авито.

## Авторизация Jira

Вход через Google открывает пользовательскую сессию Atlassian в браузере. Он **не предоставляет** локальному Go-сервису учётные данные для Jira REST API. Для live-адаптера нужен отдельный OAuth 2.0 (3LO) токен приложения либо API-токен Atlassian, настроенный вне кода. До получения прав на тестовый проект и отдельной авторизации API сценарий работает в mock-режиме.

## Проверка

1. После вопроса о доступе UI показывает источник, тестовую заявку и кнопку подтверждения.
2. Mock возвращает ключ задачи и начальный статус; после обновления страницы результат сохранён.
3. Два одинаковых подтверждения с одним ключом идемпотентности не создают две задачи.
4. Пустой ресурс, неподтверждённое действие, запрещённая роль и ошибка адаптера обрабатываются явно.
5. Live-адаптер при наличии тестового Jira-проекта создаёт задачу, затем читает её статус; UI показывает прямую ссылку.
6. Автоматические тесты и отчёт о покрытии строк прикладного кода >80%.
