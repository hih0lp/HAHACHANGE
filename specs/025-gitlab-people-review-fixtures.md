# SDD-025: Testable GitLab people and review fixtures

The isolated demo GitLab has accounts for all 12 seeded team-directory people. `intern`, `intern2`, and `approver` correspond to the chat's selectable roles; other staff have distinct GitLab accounts as well. The fixture script creates project membership and stores generated login passwords only outside Git. A second script uses each intern's GitLab API token to commit a real branch and open an MR. MR !3 is ready for mentor review; MR !4 is a draft. The older bot-authored !1/!2 remain historical fixtures and must not be described as assigned review work.

The GitLab MCP accepts a directory JWT, resolves its subject through `/v1/me`, and selects that subject's GitLab API token from a protected server-side map. GitLab itself enforces project visibility with that token. The `gitlab_review_reminders` tool emits only open non-draft MRs with the current GitLab user explicitly listed as reviewer. Browser cards therefore mean an actual assigned review, not merely an open MR. No token enters the model result or browser. The old single-subject token configuration remains supported for transition but should be removed from the active demo after the protected token map is mounted.

The chat adds the `intern2` demo role, preserving separate browser history. Login credentials and API token maps are never committed. Validate GitLab account identity and MR authors/reviewers in the GitLab UI, tool results under each role, and a denied call for an unmapped directory subject. The demo's public route and durable secret mount must be completed before calling the integration deployed.
