# SDD-025: Testable GitLab people and review fixtures

The isolated demo GitLab has accounts for all 12 seeded team-directory people. `intern`, `intern2`, and `approver` correspond to the chat's selectable roles; other staff have distinct GitLab accounts as well. The fixture script creates project membership and stores generated login passwords only outside Git. A second script uses each author's GitLab API token to commit a real branch and open an MR. MR !3 is ready for mentor review; MR !4 is a draft. The catalogue, search, and platform teams have their own authored review examples, including a platform draft. The older bot-authored !1/!2 remain historical fixtures and must not be described as assigned review work.

The GitLab MCP accepts a directory JWT, resolves its subject through `/v1/me`, and selects that subject's GitLab API token from a protected server-side map. GitLab itself enforces project visibility with that token. The `gitlab_review_reminders` tool emits only open non-draft MRs with the current GitLab user explicitly listed as reviewer. Browser cards therefore mean an actual assigned review, not merely an open MR. No token enters the model result or browser. The old single-subject token configuration remains supported for transition but should be removed from the active demo after the protected token map is mounted.

The chat adds the `intern2` demo role, preserving separate browser history. Login credentials and API token maps are never committed. The GitLab browser address is `http://100.105.236.12:18929` on the server's Tailscale network, so a user can sign in from a Mac or another Tailscale-connected device. The browser login uses each person's GitLab username and password; the chat-to-GitLab binding uses a separate PAT for that person. The external URL must match the browser address so links in MR notifications open correctly.

Generated passwords and PATs belong in `D:\HackChange\private\bobby-gitlab-demo`, readable only by the server account and Docker. They must survive container recreation and must never enter the repository. The fixture scripts currently write `/tmp` files inside GitLab, so deployment must copy those files into the protected directory and mount the PAT map read-only into the MCP container before restart. If the private directory is inaccessible, stop deployment rather than moving secrets to the worktree.

Validate GitLab account identity and MR authors/reviewers in the GitLab UI, tool results under each role, and a denied call for an unmapped directory subject. The durable secret mount and per-person MCP deployment must be completed before calling the integration deployed.
