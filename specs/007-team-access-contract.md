# SDD-007: контракт сервиса команды и доступов

## Цель и граница

Отдельный Go-сервис представляет корпоративный каталог команды и централизованный сервис заявок на доступ. Это работающая имитация инфраструктуры Авито: несколько синтетических пользователей, сохраняемые в PostgreSQL команды, ресурсы, права и заявки, реальные проверки и решения согласующих. В рабочем пути агента нет ветки с зашитыми ответами или автоматическим фиктивным одобрением. Это не заявление об изменении прав в корпоративных системах Авито.

Бадди вызывает сервис по HTTP. Сервис является источником истины для прав **в рамках прототипа**. Jira и GitLab остаются отдельными источниками задач и PR. Бадди не получает токен в промпт модели; его сервер подставляет авторизацию при вызове инструмента.

## Идентичность

- `POST /v1/auth/login` принимает `{username,password}` по HTTPS и возвращает `{access_token,token_type:"Bearer",expires_in}`. Пароли хранятся только в виде стойких хешей. Тестовые пользователи создаются миграцией/seed, а пароли задаются вне репозитория через окружение.
- Access JWT подписывается асимметрично (RS256), содержит `iss`, `aud`, `sub`, `iat`, `nbf`, `exp`, `jti`; публичный ключ доступен по `GET /.well-known/jwks.json`. Массив `aud` содержит `ai-buddy` и `team-access`; каждый сервис проверяет своё значение аудитории.
- На всех пользовательских методах ID пользователя берётся из проверенного JWT. `user_id`, `role` и `team_id` из тела запроса не являются авторизационными данными. Актуальные роли, членство и права читаются из БД; JWT не служит снимком прав.
- Чужие заявки и профили недоступны стажёру. Согласующий видит только заявки на ресурсы, где он назначен согласующим. Все изменения прав журналируются.

## Общий формат ошибок

Ошибка: `{ "error": { "code": "string", "message": "string", "request_id": "string" } }`. Коды HTTP: `400` некорректные поля, `401` нет/истёк JWT, `403` действие запрещено, `404` объект не найден или не виден, `409` конфликт/повтор с другими параметрами, `422` невозможный переход статуса, `503` временно недоступна зависимость. Текст ошибки не раскрывает закрытые ресурсы.

## Пользовательский API

| Метод | Путь | Результат |
| --- | --- | --- |
| `GET` | `/v1/me` | `{id,display_name,roles,teams:[{id,name,mentor_id,lead_id}],current_team_id}` из БД |
| `GET` | `/v1/teams/{team_id}/resources` | Видимый участнику каталог `{id,kind,name,external_ref,url,capabilities,approver_id}`; `kind` — `jira_project`, `gitlab_project`, `confluence_space`, `environment` или расширяемое значение |
| `POST` | `/v1/access/check` | Запрос `{resource_id,capability}` → `{state:"granted|missing|pending|unknown",resource_id,capability,request_id?,checked_at}` |
| `POST` | `/v1/access-requests` | Запрос `{resource_id,capability,reason,form_values,confirmed:true}` и заголовок `Idempotency-Key`; ответ `{id,status:"pending",resource_id,capability,approver_id,created_at}` |
| `GET` | `/v1/access-requests/{id}` | Текущая заявка и допустимые для заявителя поля, включая `status`, `decision_reason?`, `updated_at` |
| `GET` | `/v1/access-requests` | Заявки текущего пользователя с пагинацией |
| `GET` | `/v1/approvals` | Ожидающие заявки назначенного согласующего |
| `POST` | `/v1/access-requests/{id}/decision` | `{decision:"approve|reject",comment?}`; доступно только назначенному согласующему |

`capability` — действие над ресурсом, например `browse_issues`, `read_repository`, `create_merge_request`, `read_space`, `use_environment`. Список допустимых действий задаётся ресурсом. `unknown` означает, что проверка не завершилась достоверно; агент не вправе трактовать это как отсутствие права.

При `approve` сервис в одной транзакции обновляет заявку, создаёт/обновляет grant и outbox-событие. При `reject` grant не создаётся. После решения `POST /v1/access/check` отражает актуальное право. Повторный `POST` с тем же ключом идемпотентности и теми же параметрами возвращает ту же заявку; с другими параметрами — `409`. Сервис не создаёт дублирующую `pending` заявку на тот же ресурс и действие для пользователя.

## События

Сервис публикует через PostgreSQL outbox в Kafka topic `team-access-events`. Версия конверта `1`:

`{event_id,type,occurred_at,subject_id,team_id,resource_id,capability,request_id?,revision}`.

Типы: `access.requested`, `access.approved`, `access.rejected`, `access.revoked`, `membership.changed`. `event_id` уникален, `revision` монотонно растёт в рамках объекта. Повторная доставка допустима; потребитель применяет событие идемпотентно. JWT, пароль, текст причины и персональные данные в Kafka не передаются. Бадди связывает событие с сохранённым экземпляром сценария и пересчитывает следующий шаг.

## Инварианты и приёмка сервиса

1. Стажёр без `browse_issues` видит `missing`, подаёт заявку, а другой пользователь-согласующий её одобряет; после этого проверка возвращает `granted`.
2. Отказ не выдаёт право и сохраняет понятную причину. Стажёр не одобряет свою или чужую заявку.
3. Другой стажёр не видит профиль, права или заявки первого; подмена `user_id`/`role` в JSON ничего не меняет.
4. Повтор подтверждения с тем же ключом не создаёт вторую заявку. Перезапуск контейнера не теряет пользователей, права, заявки и outbox.
5. Событие Kafka публикуется после устойчивой записи; повтор публикации не приводит к повторной выдаче права.
6. Рабочий сервис не содержит режима `mock`. Тестовые двойники допускаются только внутри автоматических тестов.

## Разделение работы

Второй агент владеет `cmd/team-access/`, `internal/teamaccess/`, `migrations/team_access/`, собственной SDD-реализацией и тестами сервиса. Основной агент владеет `cmd/server/`, `internal/scenario/`, веб-интерфейсом, `compose.distributed.yml`, инструментами бадди и сквозной интеграцией. Изменения общих зависимостей согласуются через отдельную ветку второго агента и интеграционный коммит основного агента.
