# SDD-006: Распределённые задания AI-buddy

## Контракт

API принимает вопрос, создаёт `request_id` и запись владельца в PostgreSQL. В той же транзакции создаёт outbox-событие. Отдельный publisher отправляет событие в Kafka; повторная публикация допустима. API возвращает `202` только для сохранённого запроса. Воркеры отдельными Docker-контейнерами читают Kafka consumer group и подтверждают offset после устойчивого сохранения результата.

Redis хранит краткоживущий снимок статуса для быстрого чтения. PostgreSQL остаётся источником истины. WebSocket и HTTP читают общее состояние, поэтому запрос доступен через любой экземпляр API без sticky sessions. При потере Redis статус восстанавливается из PostgreSQL.

## Состояния и ошибки

`queued → running → completed/failed`. Воркер захватывает задание условным обновлением PostgreSQL с lease. Если воркер погиб, истёкший lease позволяет другому обработать повторное сообщение Kafka. Конечный результат записывается условно по ID lease, предотвращая позднюю запись старого воркера. Ошибки LLM повторяются ограниченное число раз; после исчерпания попыток запрос получает `failed` и диагностическое сообщение без секретов.

Сообщение Kafka не удаляется после чтения или доставки в браузер. Offset подтверждается после записи результата. Повторное сообщение для уже завершённого ID подтверждается без вызова Qwen.

## Права и данные

В демо-режиме пользователь выбирает синтетический профиль. Производственная идентичность должна поступать от существующего корпоративного провайдера, а не из произвольного заголовка браузера. `GET /v1/jobs/{id}` и WebSocket сверяют владельца. Данные Qdrant фильтруются по разрешённой области до передачи LLM. Действия Jira требуют отдельного подтверждения и устойчивого ключа идемпотентности.

## Проверка

1. API и два воркера запускаются отдельными контейнерами Compose вместе с Kafka, Redis, PostgreSQL и Qdrant.
2. Запрос остаётся доступным после рестарта API; два API экземпляра видят один статус.
3. Падение воркера во время Qwen не теряет запрос; повтор завершает его под тем же ID.
4. Повтор Kafka-сообщения не создаёт второй ответ или вторую Jira-заявку.
5. Потеря Redis не уничтожает результат; HTTP читает PostgreSQL.
6. Чужой пользователь не получает запрос по известному ID.

Автоматизированный прогон: `scripts/test-coverage.sh` с отдельной PostgreSQL. Проверяются outbox-транзакция, идемпотентное выполнение повторного сообщения, исчерпание попыток, восстановление lease и запрет позднему воркеру перезаписывать новый результат. Kafka I/O заменён только в тестовом процессе; живой брокер требует отдельного smoke-теста.
