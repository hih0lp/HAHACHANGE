## 4. Что придумала команда и что реализовано

### Бобби и знания

Бобби — универсальный ИИ-помощник стажёра, а не только поисковик. На общие вопросы отвечает локальная модель без обязательных ссылок; по задачам, людям, правилам и правам должен опираться на документы или подключённые сервисы и указывать источник рядом с фактом. Источники RAG: открытый Playbook и выдержка чек-листа; Qdrant хранит текст, метаданные и векторы, TEI строит эмбеддинги. Системный промпт в `cmd/server/answer.go`; SDD — `specs/001-playbook-rag.md`, `009-bobby-role-general-questions.md`. Нет автоматического обнаружения новых сервисов: серверу нужен известный адрес и адаптер.

### Сценарий «первая задача → доступ → следующий шаг»

Два отдельные Go-сервиса: `cmd/server` (Бобби) и `cmd/team-access` (каталог команды и доступов). В team-access синтетические `intern`, `intern2`, `approver`, команда `demo-team`, ресурс `demo-jira`; пароли задаются в `.env` и хешируются bcrypt. Вход выдаёт RS256 JWT и JWKS. PostgreSQL хранит пользователей, членство, ресурсы, grants, заявки, аудит и outbox. Стажёр проверяет `browse_issues`, подаёт заявку с обоснованием и `Idempotency-Key`; назначенный другой пользователь одобряет/отклоняет. После одобрения grant меняется в транзакции, событие публикуется в Kafka. Бобби получает событие, помечает сценарий на перепроверку и затем повторно проверяет право через сервис. См. `specs/013-team-access-contract.md`, `014-team-access-implementation.md`, `012-team-access-client-integration.md`.

Форма сейчас расположена **на `/onboarding`**, а не в основном чате: поле обоснования и подтверждение. `form_values` отправляется пустым объектом; динамических полей под разные ресурсы пока нет. Обычный чат может **читать** проверенный профиль, каталог и статус прав после входа на `/onboarding` в той же вкладке (JWT хранится в `sessionStorage`). Чат пока не создаёт заявки по естественному запросу. JWT не включается в модель, БД заданий или Kafka; worker получает только снимок проверенных данных. Это право **в учебном прототипе**, не реальная авторизация Jira/Авито.

Последняя сквозная проверка: стажёр создал заявку, другой пользователь одобрил, право стало `granted`, Kafka-событие обновило сценарий до `ready_for_task`; `go test ./...` и `scripts/team-access-smoke.ps1` прошли. В результате этих проверок **оба демо-стажёра (`intern`, `intern2`) уже имеют grant на `demo-jira/browse_issues`**; форма заявки для них сейчас может не появиться. Для новой демонстрации нужен отдельный пользователь без grant либо контролируемый сброс тестовых данных.

Состояние `ready_for_task` означает готовность выбрать задачу. Автоматическое назначение конкретной первой Jira-задачи и путь до GitLab PR **не реализованы**; это открытая часть исходной идеи. Не заявлять на защите, что весь путь до PR уже работает.

### Jira, напоминания, чат

- Jira MCP на `/mcp` читает задачу по ключу и до 10 недавних задач проекта SCRUM; Бобби добавляет свежий результат в контекст. Это учебная Jira, не внутренняя система Авито. Конфигурация и границы — `specs/004-jira-mcp.md`. Ранние тестовые задачи: SCRUM-1, SCRUM-2, SCRUM-5; их текущий статус надо запрашивать заново.
- Напоминание стажёру о незакрытой назначенной задаче в Jira появляется за `REMINDER_HOURS_BEFORE` (сейчас 24) до конца календарного дня дедлайна. WebSocket обновляет открытый чат, HTTP служит резервом. Это **один демо-стажёр** с `REMINDER_INTERN_ACCOUNT_ID`, не многопользовательская система уведомлений и не фоновая доставка. См. `specs/007-intern-deadline-reminders.md`.
- В распределённом режиме задания, результаты и история чата хранятся в PostgreSQL `ai_jobs`, Kafka передаёт задания worker, Redis ускоряет статус, WebSocket показывает прогресс. История привязана к подписанной демо-cookie браузера, не к JWT-личности; максимум 100 записей. См. `specs/006-distributed-jobs.md`, `008-chat-history.md`.
- Главная страница — простой чат без «учебного пространства команды» и старой тестовой Jira-формы. Сценарий `/onboarding` — отдельная страница. `JIRA_MODE=mock` в рабочем сервисе отвергается; прежний маршрут создания Jira-заявки отключён.

## 5. Идеи, которые обсуждали, но не следует считать готовыми

1. Довести один глубокий сценарий до первой реальной учебной задачи и PR: после подтверждённого grant выбрать задачу из Jira, показать статус/следующий шаг, затем читать GitLab PR через отдельную интеграцию. Для каждого действия нужны полномочия, подтверждение и источник результата.
2. Встроить форму доступа и её статус прямо в чат Бобби, если это улучшит единый пользовательский путь. Сейчас форма только на `/onboarding`; поля заявок к разным ресурсам не описаны в источниках Авито, их нельзя выдавать за настоящие.
3. Улучшить идентичность: убрать отдельную демо-cookie, привязать историю и задания к проверенному JWT `sub`, обеспечить изоляцию нескольких пользователей и повторную авторизацию. Демо-права не масштабировать как корпоративные.
4. Напоминания: обсуждался пинг наставника при просрочке, но команда **отложила** эту идею. Текущий выбранный вариант — напоминать стажёру за X часов. Отправка в чат при закрытой вкладке, журнал доставок и персональная настройка пока не сделаны.
   Обсуждалось также определение тимлида по Jira: постановщик задачи (`reporter`) не обязательно является тимлидом, а `accountId` Jira не обязан совпадать с ID в нашем сервисе. Для такой функции нужен явный проверенный маппинг учётных записей и каталог команды; нельзя выводить наставника или руководителя из автора задачи без источника.
5. Метрики пользы: время до первой самостоятельной задачи, доля завершённых сценариев, число повторных вопросов наставнику, время до выданного доступа, ошибки/отказы и оценка понятности ответа. Это предложения для презентации, базовые значения Авито не предоставлены.
6. Подготовить презентацию, короткое видео пути от запроса до результата, инструкции тестовым пользователям, актуальный отчёт покрытия >80% на текущем коде и проверку запуска экспертом. `TEST_REPORT.md` необходимо обновить после новой проверки.

## 6. Технические ориентиры и команды

Основной Compose `docker-compose.yml` держит Qdrant и embeddings. `compose.distributed.yml` запускает Бобби, worker, PostgreSQL, Redis, Kafka и team-access; gateway слушает `127.0.0.1:18000` и `100.105.236.12:18000`. Конфигурация LLM — `LLM_URL`, `LLM_MODEL`; Jira — `JIRA_MODE`, `JIRA_BASE_URL`, `JIRA_PROJECT_KEY`, `JIRA_EMAIL`, `JIRA_API_TOKEN`; team-access — три переменные паролей и `TEAM_ACCESS_SEED_JIRA_URL`. Значения секретов брать локально из `.env`, не печатать и не вставлять в чат.

Ранние решения о совместной работе: Mac сокомандника получал файлы через SMB по Tailscale; SSH на Windows не работал, поэтому монтирование папки не давало удалённого запуска Docker. Сейчас общая веб-ссылка на Бобби идёт по Tailscale IP. LM Studio работает на Windows, и Go worker обращается к локальному HTTP API модели через `LLM_URL`; папка проекта сама по себе не «содержит» модель. Сервис доступов подключён явным адаптером и `TEAM_ACCESS_URL`, а не автообнаружением сети. Контракт team-access требует HTTPS для login; текущий стенд открывает HTTP только на localhost и Tailscale IP. Перед внешней публикацией вне tailnet нужен TLS и проверка модели авторизации.

```powershell
cd 'C:\Users\ADMIN\Desktop\Hack&Change\avito-rag'
go test ./...
.\scripts\team-access-smoke.ps1
docker compose -p avito-rag-distributed -f compose.distributed.yml ps
docker compose -p avito-rag-distributed -f compose.distributed.yml logs --tail 50 api worker team-access
```

Состояние контейнеров, Jira, Qdrant и tailnet меняется: новый чат должен проверить их перед утверждением, что сервис доступен. При последней проверке gateway, API, worker, PostgreSQL, Redis, Kafka, team-access, Qdrant и embeddings работали; старый API на 8000 был остановлен. Свободного места на C: оставалось около 1 ГБ — Docker ранее падал при заполнении диска; не запускать тяжёлую пересборку без проверки места.
